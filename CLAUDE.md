# CLAUDE.md

Решение команды 049 для трека манипуляции nssr-polygon: узлы ROS 2 Humble, которые управляют роботом TienKung 2.0 Pro
в симуляторе Isaac Sim. Пул объектов 4 (figure, dish, box). Подход и архитектура: `docs/ANALYSIS.md`,
`docs/ARCHITECTURE.md`, план: `docs/ROADMAP.md`, процесс: `CONTRIBUTING.md`.

## Симулятор лежит в соседнем репозитории

`../nssr-uwt-polygon` (если клон в другом месте, путь указан в `CLAUDE.local.md`). **Только чтение**: решение не
должно зависеть от правок симулятора, на проверке будет оригинал. Связь с ним только через ROS 2.

Где что смотреть (читать по мере надобности, а не целиком):

поведение. Использовать его в решении нельзя.

## Жёсткие правила хакатона

- Положение объектов, стола, ящиков, штативов и шкафа определяем только по датчикам робота: камеры, глубина,
  `/joint_states`, `/arm_6dof_*`, `/inspire_hand/state/*`, `/tf`. Заранее измеренные координаты сцены в код не зашивать.
  Можно примерные границы поиска, размеры из документации, `/sim/task` и геометрию робота. Нельзя читать USD, состояние
  физики, API Isaac и импортировать код симулятора.
- В `src/` и `run.sh` нельзя обращаться к `/sim/task/check`, `/sim/objects/set`, `/sim/objects/randomize`:
  на проверке они отключены, а обращения к ним фиксируются. Отладочные скрипты кладём в `tools/`.
- Один `run.sh` для всех задач. `/sim/task/done` публикуется в любом исходе.
- В контейнере решения нет файлов симулятора. Всё, что нужно в рантайме (URDF, веса), должно лежать
  в этом репозитории или скачиваться в `setup.sh`.
- Проверяется последний коммит в `main`: туда попадаем только через PR, и `main` всегда должен работать.
- Перед коммитом: `bash tools/check_rules.sh`.

## Соглашения

- Система координат API — `pelvis`, единицы СИ, время только из `/clock` (`use_sim_time: true`).
- Интерфейсы в `src/hack_interfaces` меняем только по договорённости команды: от них зависят все модули.
- Скорость моторов ограничена 0.8 рад/с; приводы недолетают до цели, поэтому контур замыкаем по `/joint_states`.
- Миссия brain идёт в отдельном потоке, узлы крутятся в `MultiThreadedExecutor`. Синхронно ждать внутри callback нельзя.

## Сборка и запуск

Локально ROS и docker нет. Симулятор и решение работают на общем GPU-сервере, туда ходим только через
`bash tools/remote.sh ...` (подробно: `docs/SERVER.md`). Код правим здесь, на сервер он копируется командой `sync`,
коммит для этого не нужен.

- Прогон как на проверке: `bash tools/remote.sh eval sort3 --pool 4 [--seed S]`. Долгий, запускай в фоне.
- По частям: `sim start sort3 --pool 4`, `solution`, `solution wait 600`, `check`, `sim stop`.
- ROS к работающему симулятору: `bash tools/remote.sh ros ros2 topic list`.
- Сборка и запуск отдельных узлов: `bash tools/remote.sh dev -- 'colcon build --symlink-install && ros2 run ...'`.
  Контейнер `nssr-dev-<имя>` остаётся запущенным, `build/` и `install/` лежат в его копии и переживают `sync`.
  torch и cuRobo берутся из образа: `bash tools/remote.sh dev-image` один раз и после смены установки. `bash setup.sh`
  и `bash tools/curobo_install.sh` в команды `dev` не добавляй: они тратят минуты.
- Логи: `logs sim|solution [N]`, память против бюджета 16 ГБ VRAM и 32 ГБ RAM: `gpu`. Кадры и rosbag: `fetch`.
- Логику без ROS (task.py, grasp_planner.py) проверяем локально обычным python3 с заглушками geometry_msgs.

Стенд один на команду: `sim start` занимает его за тобой, `sim stop` освобождает. Чужой стенд (`status`) не
перехватывай через `--force`, скажи человеку. Если сессий несколько, у каждой своё имя: `NSSR_WHO=jobs-a bash
tools/remote.sh ...`, иначе замок их не различает. `dev` замок не проверяет и подключается к чужому симулятору: перед ним смотри `status`. Повторный `dev` с тем же именем останавливает только предыдущую команду в своём контейнере. Если `remote.sh` не может подключиться, не делай выводов о работе
кода: попроси человека проверить сервер.
